# Traductions et langues

Moteur : `src/utils/translationUtils.ts` — sans dépendance, pour éviter les cycles
État : `src/components/language/LangEngine.tsx` — `LangContext`, persiste dans `localStorage`
Sélecteur : `src/components/dropdowns/DropdownLang.tsx`, alimenté par `availableLanguages`
Textes : **exclusivement** dans `src/assets/`, jamais dans un composant

Le système est **complet côté contenu**. Français et anglais, zéro chaîne en dur dans
`src/components/` et `src/pages/`. Ce qui manque est ailleurs : la validation et le SEO.

## La convention réelle : l'anglais vit sous `UNIVERSAL_LANG`

`UNIVERSAL_LANG` vaut `"0"`. Il désigne le contenu identique dans toutes les langues
(« React », « CV », « Blog »), **et sert de repli par défaut**. En pratique, la plupart des
objets du dépôt écrivent le français sous `fr` et l'anglais sous `[UNIVERSAL_LANG]` :

```ts
content:
{
    fr: "À propos",
    [UNIVERSAL_LANG]: "About",
},
```

Une clé `en` explicite est rare. Suivre la convention majoritaire plutôt que d'introduire
`en` dans un objet qui utilise `[UNIVERSAL_LANG]`.

La chaîne de repli de `getContent()` est : `content[lang]` → `content[UNIVERSAL_LANG]` →
`fallback` → première valeur disponible → `""`.

## ⚠️ Le validateur ne vérifie presque rien

`validateMultilingual` (`src/assets/dataConsistency.ts:62`) **saute entièrement le contrôle
par langue dès que la clé `UNIVERSAL_LANG` est présente** :

```ts
if (!keys.includes(UNIVERSAL_LANG)) {
    SUPPORTED_LANGUAGES.forEach(lang => { /* … warn … */ });
}
```

Comme presque tout le contenu porte cette clé, `npm run validate` ne remonte **aucun**
avertissement « Missing translation » aujourd'hui — non pas parce que tout est traduit,
mais parce que le contrôle ne s'exécute pas.

Conséquence directe : **ajouter une troisième langue ne produira aucun avertissement**, même
en n'en traduisant rien. Le repli affichera l'anglais partout, silencieusement. Il n'y a
donc pas de filet automatique pour un chantier de traduction — il faut le construire ou
tenir la liste à la main.

## Traduire l'existant

Le repli masque les manques : un texte non traduit s'affiche en anglais au lieu de crier.
Pour trouver ce qui manque réellement, chercher les objets multilingues sans clé `fr` :

```bash
grep -rn 'UNIVERSAL_LANG\]:' src/assets --include=*.ts | wc -l
```

puis inspecter les objets concernés — beaucoup sont légitimement universels (noms de
technologies, titres propres).

**Le piège central** : les composants indexent en direct, `entry.description[currentLang]`,
au lieu d'appeler `getContent()` / `translate` qui existent exactement pour la chaîne de
repli. L'indexation directe rend `undefined` en silence quand la clé manque. Quelques
composants compensent à la main (`project.title[currentLang] || project.title[UNIVERSAL_LANG]`
dans `ProjectPreview.tsx`), la plupart non.

Câbler un composant sur `translate` est un vrai correctif, mais il touche beaucoup de
fichiers : **le proposer, ne pas l'appliquer d'office**.

## Ajouter une langue

Dans cet ordre :

1. **`SUPPORTED_LANGUAGES`** dans `src/utils/translationUtils.ts`. Le type
   `SupportedLanguage` en découle automatiquement.
2. **`countries`** dans `src/assets/uiConstants.ts` si le pays n'y est pas : `{ symbol,
   label, phoneCode }`.
3. **`availableLanguages`** (`src/assets/uiConstants.ts:826`) — un `countries.find()` par
   langue proposée dans le sélecteur.
4. **Tout le contenu** de `src/assets/` : `contents.ts`, `uiConstants.ts` (1212 lignes),
   `skills.ts`, `projects/*`, `blog/*`, `seoConstants.ts`. Ajouter la clé à chaque objet
   multilingue **qui n'est pas universel**.
5. **Les binaires par langue** : `src/assets/documents/index.ts` (le CV a une version `fr`
   et une sous `[UNIVERSAL_LANG]`).
6. **Le validateur** : sans intervention il restera muet (voir plus haut). Si l'ajout doit
   être fiable, c'est le moment de revoir le court-circuit `UNIVERSAL_LANG` de
   `validateMultilingual` — en gardant à l'esprit qu'il est là pour une raison, puisque le
   contenu réellement universel n'a pas à être traduit.
7. **`getLocalLanguage()`** (`src/utils/utils.ts`) : repli `localStorage.lang` →
   `navigator.language.slice(0, 2)` → `'fr'`. Rien à changer pour une langue de plus, mais
   c'est là que se décide la langue au premier chargement.

## Limites structurelles

À annoncer avant tout chantier i18n ambitieux — aucune ne se règle en ajoutant des
traductions :

- **Pas de locale dans l'URL.** `/`, `/projects`, `/blog/:slug` sont partagées par toutes
  les langues. La langue est un état client dans `localStorage`, invisible des moteurs de
  recherche et non partageable par lien.
- **Pas de `hreflang`, pas de `og:locale`.** `MetaTags.tsx` ne prend pas de langue en
  entrée ; `HomeSEOConstants` et `BlogSEOConstants` sont des chaînes anglaises uniques.
  Seul le JSON-LD déclare `inLanguage: ['en', 'fr']`.
- **`index.html` sert `lang="en"` en dur**, corrigé par `LangEngine` après hydratation.
- **Le sitemap n'a pas d'alternates** par langue.
- **`CareerTimeline.tsx` trie sur `period['fr']` en dur** — le tri casse si la clé `fr`
  disparaît d'une entrée.

## Vérifier

```bash
npm run lint && npm run build && npm run validate
```

Puis, à l'œil, dans chaque langue : le sélecteur, la home, un projet, un article. Le
validateur ne couvrira pas les manques de traduction.
